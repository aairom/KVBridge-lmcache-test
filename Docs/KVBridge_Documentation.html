KVBridge — Developer Documentation

An LMCache-style KV cache management layer for local (llama.cpp, Ollama) and cloud (OpenAI-compatible) LLM inference engines, with a Gradio GUI that makes cache hits, tier usage and latency gains visible. The engine is chosen and configured in the GUI or in .env; nothing is hard-coded.

Python 3.12Gradio 6blake3llama.cpp slots APIOllama RESTOpenAI-compatible APIApache-2.0macOS / Linux, cloud optional

1. Application overview & purpose

KVBridge demonstrates the core value proposition of LMCache — a KV cache management layer for scalable LLM inference — on a developer laptop. LMCache itself targets server-side engines (vLLM, SGLang, TensorRT-LLM) and needs CUDA. KVBridge re-implements the LMCache concepts (chunked, content-addressed KV reuse; tiered storage; engine-independent keys) on top of the engines developers actually run: two local ones (llama.cpp, Ollama) and any OpenAI-compatible cloud service, all behind one pluggable engine registry.

What KVBridge is, and is not KVBridge is an LMCache-style implementation. It is not the LMCache package. It optionally reuses LMCache's native TokenHasher when the real package can be built (scripts/install_lmcache.sh); otherwise a bit-compatible blake3 rolling hash is used.

1.1 Why it exists

Prefill (processing the prompt into a KV cache) dominates time-to-first-token (TTFT) for long, repeated prefixes such as documents, system prompts and chat histories. If the KV tensors for a prefix already exist, the engine can skip that compute. KVBridge makes that visible and measurable with three comparable modes:

ModeBehaviourPurpose
coldNative cache erased, cache_prompt=false. Every request recomputes the full prompt.Baseline
nativeEngine's own in-slot prefix reuse (cache_prompt=true). Lost on restart / eviction.What you get for free
lmcacheKVBridge tiered store: chunk-hash lookup, KV snapshot restore from RAM (L1) or disk (L2), save on miss.Managed, persistent cache

2.3 Hashing & cache keys

Each prompt is tokenised, split into fixed-size chunks (default 256 tokens) and hashed with a rolling prefix hash, so chunk i's key depends on every earlier chunk. Equal keys therefore imply equal prefixes. A partial tail chunk is discarded.

# h_0 = seed(namespace)
h_i = blake3( h_{i-1} || pack_be_uint32(chunk_i) )

# namespace = "{backend.name}|{model_id}"  -> isolates models and engines
  • Tokens are packed as big-endian uint32.
  • make_hasher(chunk_size, ns, prefer_lmcache) returns LMCacheHasherAdapter when the real package is importable and requested, else ChunkHasher.
  • common_prefix_len(a, b) is a small helper returning how many leading tokens two sequences share (a utility; the engine itself matches on chunk hashes).

2.4 Tiered store

TieredStore internals: lookup (longest cached prefix), chunk_status (per-chunk L1/L2/none for the chunk map), fetch, put, _drop_superseded (a longer snapshot replaces shorter ones with the same prefix), _make_room_l1 / _make_room_l2 (LRU eviction), _write_l2, _save_index / _load_index, clear(tiers), resize, stats, entries.

2.5 Cached engine & modes

CachedEngine.infer() holds an RLock, routes to _infer_full if backend.supports_kv_export else _infer_shadow, and records any exception on the RequestRecord.

kvbridge/engine.py — _infer_full (abridged)
def _infer_full(self, prompt, rec, n_predict, temperature):
    b = self.backend
    tokens = b.tokenize(prompt)
    if rec.mode == "cold":
        b.reset_native_cache()
        self._fill(rec, b.generate(prompt, tokens, n_predict, False, temperature)); return
    if rec.mode == "native":
        self._fill(rec, b.generate(prompt, tokens, n_predict, True, temperature)); return

    # ---- lmcache mode
    hashes = self.hasher.chunk_hashes(tokens)
    rec.chunks_total  = len(hashes)
    rec.chunk_status  = self.store.chunk_status(hashes)   # drives the chunk map
    b.reset_native_cache()                               # engine lost its own KV
    match = self.store.lookup(hashes)
    rec.lmcache_match_tokens, rec.chunks_hit, rec.tier = match.tokens, match.chunks, match.tier
    if match.entry is not None:
        try:
            blob = self.store.fetch(match.entry)         # L1, else L2 (promoted to L1)
            n = b.restore_state(blob)                    # POST /slots/0?action=restore
        except (BackendError, KeyError, OSError) as exc:
            log.warning("restore failed (%s); falling back to recompute", exc)
            rec.chunks_hit, rec.lmcache_match_tokens, rec.tier = 0, 0, "none"
            b.reset_native_cache()
    res = b.generate(prompt, tokens, n_predict, True, temperature)
    self._fill(rec, res)
    if len(hashes) > rec.chunks_hit:                    # new chunks were computed -> store
        blob, n_saved = b.save_state()                   # POST /slots/0?action=save
        self.store.put(hashes, len(hashes) * self.s.chunk_size, blob,
                       note=f"{n_saved} tok snapshot")
Granularity Chunk hashes are used for matching (how much of a prefix is covered). Storage granularity is a whole-slot snapshot, because llama.cpp saves/restores a slot, not individual chunks.

2.6 Configuration

Every engine setting can be changed in the GUI (tab 1 — Engine & Cache) or through KVB_* environment variables / .env (copy .env.example, which documents every variable and is covered by a test). Settings.validate() checks the shared values (chunk_size, ctx_size ≥ chunk_size, tier sizes, request_timeout) and then calls the selected engine's check_settings(): llama.cpp (port validity, reserved ports, start timeout), Ollama (URL, model), cloud (URL or preset, model, API style, max-tokens field, budget, extra-headers JSON, and no API key over plain http to a non-loopback host). main() turns any problem into a SystemExit before anything starts. In the GUI, Settings.apply() coerces the form values, validates a candidate copy and commits only if it is valid, so a bad edit never leaves the app half-configured.

Secrets

  • The GUI key box is a password field that is never pre-filled; leaving it blank keeps the current key.
  • The key can live outside any file: set KVB_CLOUD_API_KEY_ENV to the name of an exported variable.
  • Show effective configuration prints Settings.to_display() with secrets masked. Keys are redacted from backend error text and are never written to logs or output/ exports.
  • Save settings to .env uses update_env_file(): comments and order are preserved, missing keys are appended, values are quoted, the write is atomic with file mode 0600, newlines are rejected. The key is written only when Also write the API key is ticked (off by default). .env is git-ignored.

3. Lifecycle management

KVBridge owns up to two processes: the GUI process (python -m kvbridge) and, optionally, a managed llama-server child. Lifecycle code exists to guarantee that the child never outlives the GUI.

3.1 Startup sequence

  1. Launch. scripts/start.sh starts python -m kvbridge through a tiny Python Popen(start_new_session=True) so the GUI survives the terminal closing. PID → output/kvbridge.pid, log → output/logs/kvbridge.log.
  2. Configure. Settings.from_env() reads KVB_* and .env; settings.validate() aborts with SystemExit("Invalid configuration: ...") on any problem.
  3. Build. AppState(settings) (no engine yet), build_app(state), then demo.queue(default_concurrency_limit=4).
  4. Announce. Prints KVBridge GUI: http://host:port.
  5. Install signal handler for SIGTERM (see below).
  6. Serve. demo.launch(...) inside try; finally stops the engine if one is connected.
  7. Wait. start.sh polls the URL for up to 60 s and prints KVBridge is running: http://127.0.0.1:7871 (pid N, log: ...); if the process dies it prints the log tail and exits 1.

3.2 SIGTERM handling

Python's default disposition for SIGTERM terminates the interpreter immediately, without unwinding the stack: finally blocks and atexit handlers do not run. scripts/stop.sh sends SIGTERM, so without a handler the managed llama-server would be orphaned. KVBridge converts SIGTERM into a normal interpreter exit.

kvbridge/app.py — main()
def main() -> None:
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s: %(message)s")
    settings = Settings.from_env()
    problems = settings.validate()
    if problems:
        raise SystemExit("Invalid configuration: " + "; ".join(problems))
    state = AppState(settings)
    demo = build_app(state)
    demo.queue(default_concurrency_limit=4)
    print(f"\n KVBridge GUI:  http://{settings.gui_host}:{settings.gui_port}\n", flush=True)
    # Turn SIGTERM (scripts/stop.sh) into a normal exit so ``finally`` stops the
    # managed llama-server instead of leaving it orphaned.
    signal.signal(signal.SIGTERM, lambda *_: sys.exit(0))
    try:
        demo.launch(server_name=settings.gui_host, server_port=settings.gui_port, show_error=True,
                    css=CSS, theme=gr.themes.Soft(primary_hue="blue"), inbrowser=False)
    finally:
        if state.engine:
            state.engine.stop()

sys.exit(0) raises SystemExit in the main thread, which propagates out of demo.launch(), runs finally, and calls CachedEngine.stop() → LlamaCppBackend.stop() (see section 8). Ctrl-C (SIGINT) already raised KeyboardInterrupt and took the same path.

4.2 AppState & the connect handler

kvbridge/app.py — AppState
class AppState:
    """Process-wide mutable state shared by all GUI callbacks."""
    def __init__(self, settings):
        self.settings = settings
        self.engine: Optional[CachedEngine] = None
        self.last_status: list[str] = []
        self.last_label = ""
        self.lock = threading.RLock()

    def require(self) -> CachedEngine:
        if self.engine is None:
            raise gr.Error("Not connected. Open the 'Engine & Cache' tab and click Connect.")
        return self.engine
  • Handlers that need an engine call state.require(); users see a Gradio error toast instead of a traceback.
  • connect(...) runs under state.lock: stop previous engine → form_to_values → Settings.apply() (coerce, validate a candidate copy, commit atomically; problems are listed per field and nothing changes) → CachedEngine(s, make_backend(s.engine, s)).start(). A blank API-key box keeps the current key. BackendError becomes readable status text (with keys redacted); unexpected exceptions are logged and shown.
  • Gradio queue concurrency is 4, while CachedEngine.infer() serialises engine access with its own RLock (one llama.cpp slot).

6. Engine integration: llama.cpp, Ollama & cloud

All engines implement the abstract Backend interface (start, stop, is_ready, tokenize, generate, reset_native_cache, save_state, restore_state, describe plus the class attributes kind and supports_kv_export and the classmethod check_settings) and are created by make_backend(kind, settings), which resolves the name through the engine registry (llamacpp/llama, ollama, cloud/openai/api) and raises BackendError listing the valid choices otherwise. GenResult normalises timings across engines.

6.1 llama.cpp — full integration

LlamaCppBackend drives llama-server over HTTP, with one slot (-np 1, id_slot: 0), so exactly one prefix is live at a time and the slot save/restore API acts on it.

6.2 Ollama — shadow mode

Ollama exposes no API to read or write KV tensors and no tokenizer endpoint, so KVBridge cannot store its cache. It still runs the whole LMCache-style control plane next to Ollama and uses Ollama's own counters as ground truth.

In shadow mode (_infer_shadow):

  1. Pseudo-tokenise the prompt and compute chunk hashes; cold first calls reset_native_cache().
  2. lmcache looks the hashes up in the store (accounting only).
  3. Ollama generates normally; its prompt_eval_cached_count becomes server_cached_tokens.
  4. Predicted match tokens are scaled by prompt_tokens / len(pseudo_tokens) so numbers are comparable with Ollama's real tokens.
  5. On a miss, a virtual entry (no blob, note shadow (accounting only), size from kv_bytes_per_token) is recorded so hit rates, tier usage and the chunk map still work.
Honest reading In shadow mode the savings come from Ollama's prefix cache; KVBridge predicts and measures them. Records carry shadow=true and the GUI labels the mode “SHADOW”.

7. Connection flow & managed-server spawning

7.1 Connect sequence

CachedEngine.start() additionally refreshes the hasher and the store directory, then loads the persisted index. The namespace "{backend.name}|{model_id}" seeds the hash and selects a per-model sanitised store directory, so different models/engines never see each other's snapshots (a snapshot is only valid for the same model file and context size).

7.2 Managed-server spawning

LlamaCppBackend.start() evaluates, in order:

  1. Attach if healthy. If is_ready() (HTTP 200, status: ok on /health), reuse the running server and _probe() it. Nothing is spawned and self.proc stays None, so stop() will not kill someone else's server.
  2. External but down. If KVB_LLAMA_URL is set and unreachable → BackendError("external llama-server not reachable at ...").
  3. Port conflict. If the managed port answers but is not a healthy llama-server → BackendError("port N is busy but not a healthy llama-server; change KVB_MANAGED_PORT").
  4. Spawn. Build the command, create the log directory, open output/logs/llama_server.log (append), and subprocess.Popen(..., stdout=log, stderr=STDOUT, start_new_session=True).
  5. Record the PID in output/llama_server.pid (used by stop.sh as a safety net).
  6. Wait for readiness up to KVB_LLAMA_START_TIMEOUT seconds (default 180), every 0.5 s. If the process exits early → BackendError("llama-server exited with code N; see ...llama_server.log"). On timeout it calls stop() before raising.
  7. Probe /slots for the real n_ctx.
kvbridge/backends.py — LlamaCppBackend.start() (excerpt)
self.proc = subprocess.Popen(cmd, stdout=logf, stderr=subprocess.STDOUT,
                             start_new_session=True)         # own session + process group
self.pidfile.write_text(str(self.proc.pid))
deadline = time.time() + self.s.llama_start_timeout   # KVB_LLAMA_START_TIMEOUT
while time.time() < deadline:
    if self.proc.poll() is not None:
        raise BackendError(f"llama-server exited with code {self.proc.returncode}; "
                           f"see {self.s.log_dir / 'llama_server.log'}")
    if self.is_ready():
        self._probe(); return
    time.sleep(0.5)
self.stop()
raise BackendError(f"llama-server did not become ready within {self.s.llama_start_timeout:g} s")

start_new_session=True puts the child in its own process group (pgid == pid). That is what allows stop() to signal the whole group with os.killpg and prevents a terminal Ctrl-C aimed at the GUI from also hitting the server uncontrolled.

Ports By default KVBridge refuses to use the managed ports 5000 (AirDrop on macOS), 8080, 9931 and 11434 (Ollama); the list is the KVB_RESERVED_PORTS setting. Defaults are GUI 7871 and server 8089.

7.3 Connecting to Ollama and cloud engines

  1. Ollama. GET /api/version (failure → “Ollama not reachable”), then POST /api/show for the model and its KV size. No process is spawned or stopped.
  2. Cloud. check_settings() has already confirmed URL/preset, model, API style and the https-with-key rule; start() resolves the key (KVB_CLOUD_API_KEY, else the variable named by KVB_CLOUD_API_KEY_ENV), builds the headers and probes the endpoint. A missing key, bad URL or HTTP 401/404 becomes a readable status message with the key redacted.
  3. Both then follow the same path as llama.cpp: namespace "{backend.name}|{model_id}", store index load, status text (SHADOW, location).

8. Shutdown procedures & orphan prevention

8.1 Defence in depth

Layer 1 — GUI exit path

kvbridge/backends.py — LlamaCppBackend.stop()
def stop(self) -> None:
    if self.proc and self.proc.poll() is None:
        try:
            os.killpg(self.proc.pid, signal.SIGTERM)       # whole group, graceful
            self.proc.wait(timeout=15)
        except (ProcessLookupError, subprocess.TimeoutExpired):
            try:
                os.killpg(self.proc.pid, signal.SIGKILL)   # escalate
            except ProcessLookupError:
                pass
    self.proc = None
    self.pidfile.unlink(missing_ok=True)

Idempotent: calling it twice, or when the child already exited, is harmless. External servers (proc is None) are never touched. OllamaBackend.stop() is a no-op because Ollama is an independent daemon.

Layer 2 — scripts/stop.sh

scripts/stop.sh
#!/usr/bin/env bash
# Gracefully stop the GUI and any managed llama-server it started.
set -uo pipefail
cd "$(dirname "$0")/.."

stop_pid() {  # $1=pidfile $2=name
  [ -f "$1" ] || return 0
  pid="$(cat "$1")"
  if kill -0 "$pid" 2>/dev/null; then
    kill -TERM "$pid" 2>/dev/null
    for _ in $(seq 1 30); do kill -0 "$pid" 2>/dev/null || break; sleep 0.5; done
    if kill -0 "$pid" 2>/dev/null; then kill -KILL "$pid" 2>/dev/null; echo "$2 force-killed"; else echo "$2 stopped"; fi
  fi
  rm -f "$1"
}

stop_pid output/kvbridge.pid "KVBridge GUI"
# The GUI stops its managed llama-server on exit; clean up if it was orphaned.
stop_pid output/llama_server.pid "managed llama-server"
  • Order matters: the GUI is stopped first so its own cleanup runs; only then is the server pid file consulted.
  • If Layer 1 worked, llama_server.pid is already gone and the second call is a no-op. Layer 1 is the primary mechanism; the pid-file pass is a belt-and-braces fallback.
  • cleanup.sh calls stop.sh before deleting .venv, .pytest_cache, node_modules and __pycache__.

8.2 The orphan bug (found and fixed)

Symptom After scripts/stop.sh, the GUI was gone and output/llama_server.pid was removed, but a managed llama-server kept listening on :8089 with parent PID 1 (reparented to init).
StepWhat happened
1stop.sh sent SIGTERM to the GUI.
2With no handler installed, Python used the OS default: terminate immediately. finally never ran, so engine.stop() was never called.
3The managed llama-server (own session via start_new_session=True, so it does not receive the GUI's signals) was never told to stop. It stayed alive, reparented to PID 1, while the pid file was gone.
Root causeMissing SIGTERM handler in main().
Fixsignal.signal(signal.SIGTERM, lambda *_: sys.exit(0)) (plus import signal, sys) so SIGTERM unwinds through finally.
VerificationEnd-to-end: start → Connect via GUI (spawns :8089) → stop.sh. Afterwards nothing listens on 8089 or 7871 and no pid files remain. Plus the automated regression test in section 9.
Why not rely on atexit? atexit handlers are also skipped when the process dies from an unhandled fatal signal. Only a Python-level handler converts the signal into an exception/exit that runs cleanup.

9. Regression testing for signal handling

test_sigterm_runs_cleanup in tests/test_scenarios_charts_app.py locks in the fix. It exercises the real app.main() in a child interpreter with only the heavy parts replaced, so the actual signal.signal(...) line is under test.

  1. Spawn a child Python (sys.executable -c script) with KVB_* directories pointing into tmp_path.
  2. Patch inside the child: app.build_app returns a fake Demo whose launch() prints READY and sleeps 60 s; app.AppState returns an object whose engine.stop() writes a marker file.
  3. Wait for READY on the child's stdout (30 s deadline) — this guarantees the handler is already installed.
  4. Send SIGTERM and wait(timeout=15).
  5. Assert the marker file exists, i.e. finally ran and engine.stop() was called. A finally clause in the test kills the child if it is still alive.
tests/test_scenarios_charts_app.py
def test_sigterm_runs_cleanup(tmp_path):
    """main() must turn SIGTERM into a normal exit so ``finally`` stops the engine."""
    marker = tmp_path / "cleaned"
    script = textwrap.dedent(f"""
        import sys, time
        from unittest import mock
        import kvbridge.app as app

        class Eng:
            def stop(self): open({str(marker)!r}, "w").write("ok")

        class Demo:
            def queue(self, **k): return self
            def launch(self, **k):
                print("READY", flush=True)
                time.sleep(60)

        with mock.patch.object(app, "build_app", lambda state: Demo()), \\
             mock.patch.object(app, "AppState") as st:
            st.return_value.engine = Eng()
            app.main()
    """)
    env = {**os.environ, "KVB_OUTPUT_DIR": str(tmp_path), "KVB_STORE_DIR": str(tmp_path / "s"),
           "KVB_SLOT_DIR": str(tmp_path / "sl"), "KVB_LOG_DIR": str(tmp_path / "l")}
    p = subprocess.Popen([sys.executable, "-c", script], stdout=subprocess.PIPE,
                         stderr=subprocess.STDOUT, text=True, env=env, cwd=PROJECT_ROOT)
    try:
        deadline = time.time() + 30
        while time.time() < deadline:
            if "READY" in (p.stdout.readline() or ""):
                break
        else:
            pytest.fail("child never became ready")
        p.send_signal(signal.SIGTERM)
        p.wait(timeout=15)
    finally:
        if p.poll() is None:
            p.kill()
    assert marker.exists(), "engine.stop() was not called on SIGTERM"

Abridged. The real test imports os, signal, subprocess, sys, textwrap, time inside the function and computes cwd as the project root with os.path.dirname(os.path.dirname(os.path.abspath(__file__))); PROJECT_ROOT above stands for that expression.

10. Limitations & challenges

10.1 Known limitations

LimitationDetail
LMCache-style, not LMCacheKVBridge re-implements the chunking, chained hashing and tiered-store ideas of LMCache. It does not embed the LMCache engine, because the PyPI wheel is manylinux/CUDA-only and cannot run on Apple Silicon. The real library is optional and used only for the hasher equivalence test, which is skipped when it is absent.
Whole-slot snapshotsllama.cpp slot save/restore stores the full slot, not individual chunks. Chunk hashes are the index and the hit-rate accounting; the restored state is one blob (about 70 MB per ~600 tokens).
Model- and context-boundA snapshot is valid only for the same model file and context size. Changing either requires a new cache.
Ollama is shadow modeOllama exposes no KV-state API. KVBridge runs it in shadow mode with pseudo-tokens: the store tracks what LMCache would have reused and reports Ollama's own prompt-cache counters alongside.
Cloud is shadow modeHosted APIs never expose KV tensors, so nothing can be stored or restored. KVBridge accounts for chunks and reports the provider's cached_tokens.
Cloud privacy and costPrompts leave the machine and are billed. Provider caches have a minimum prompt length (about 1,024 tokens on OpenAI), a short lifetime, and rate limits; a short or cold prompt legitimately shows 0 cached tokens. Use KVB_CLOUD_TOKEN_BUDGET, and prefer KVB_CLOUD_API_KEY_ENV over storing a key.
Provider dialect differencesOnly the OpenAI-compatible dialect is implemented. Providers that deviate (e.g. need other field names) are covered by KVB_CLOUD_MAX_TOKENS_FIELD, KVB_CLOUD_SEND_TEMPERATURE, KVB_CLOUD_EXTRA_HEADERS; native non-OpenAI APIs need a new backend.
No remote tiersOnly L1 (RAM) and L2 (disk). There is no Redis/S3 tier and no multi-instance sharing.
Warm-slot comparisonOn a warm slot, native llama.cpp prefix caching is faster than lmcache (native avg 64 ms in our run). The value of the cache layer is persistence across restarts and capacity beyond one slot.
Unused helpercommon_prefix_len in hashing.py is tested but not called by the engine.
